# Подключение SellerStatus: аудит выполнен, живые данные не подключены

Проверено 30 октября 2026 года. Локальный сервис: `chat-bot-wb`, HEAD `151a8433`; файлы соседнего проекта не менялись. Анонимный GET `https://app.sellerstatus.ru/api/v1/auth/session` вернул HTTP 401. GET `/openapi.json` вернул HTTP 200 с HTML страницы, а не JSON-схемой. В локальном `app/main.py` публикация OpenAPI выключена вне development. Эти проверки не подтверждают структуру ответов приватных маршрутов или данные кабинета.

## Схема

WB → существующий worker SellerStatus → сохранённые источники → API SellerStatus → Go-клиент → React.

Открытие панели и фильтрация должны читать данные из сервиса или локального кеша, а не запускать загрузку из WB. Кнопка обновления перечитывает сводку; запрос синхронизации — отдельное действие с серверными ограничениями.

## Контракт, который нужно согласовать

- Идентификатор кабинета и права чтения.
- Явные границы периода и часовой пояс Europe/Moscow.
- Определения заказов, выкупов, возвратов и денежных сумм.
- Время успешного обновления, статус и полнота **каждого источника**; время формирования ответа хранить отдельно.
- Остаток и движение по размерам/баркодам с фактической складской детализацией WB.
- Покрытие себестоимости, подтверждённость денежных значений и состав расходов.
- Отдельные состояния `unknown`, `stale`, `unavailable`, `partial`; ноль только для известного нулевого значения.
- Для дельты периода — сопоставимые границы и подтверждённая полнота обоих срезов.

## Найденное в локальном коде сервиса

- `/dashboard` берёт последний готовый дневной отчёт. Это не готовый контракт «на сегодня».
- В dashboard метрика `sales` имеет единицу `RUB`, а не количество выкупленных единиц. Её нельзя подставить в счётчик товаров.
- `/products` читает сохранённый inventory snapshot; часть метрик имеет фиксированный период 30 дней.
- `/products/{nm_id}` содержит товар, размеры и склады.
- Размеры и склады в `ProductDetailResponse` представлены отдельными списками. Подтверждённого объединённого списка «склад × размер × баркод» этот ответ не даёт. Из двух агрегатов нельзя выдумывать распределение; текущая таблица с баркодами остаётся демонстрационной.
- `/profit-loss` имеет расчёт, покрытие себестоимости, предупреждения и отдельную финансовую сверку. Не считать его полным финансовым фактом без проверки состава расходов.
- В inventory-сервисе есть общий кеш, single-flight и backoff.

Названия маршрутов приведены относительно существующего API. Их наличие в опубликованном сервисе, авторизация настольного клиента и реальные ответы ещё не проверены.

Авторизация существующего веб-приложения основана на сессионной HttpOnly cookie. Отдельного desktop/device-маршрута в просмотренном коде нет. WB-токен уже подключённого кабинета не заменяет авторизацию клиента SellerStatus. Для живой версии нужны отдельный согласованный способ входа, ограниченное чтение выбранного кабинета и новый агрегированный контракт; использовать браузерную cookie как вручную скопированный токен не предполагается.

## Что подготовлено в настольном проекте

- `SnapshotSource` отделён от RTK Query. Сейчас работает только `createDemoSource()`; HTTP-транспорт и Keychain не реализованы.
- До передачи в React проверяются кабинет, период, даты источников, числовые значения, складские ссылки и дубликаты. Валидатор намеренно принимает только текущий **демоконтракт** (`isDemo: true`). Живой контракт с неизвестными значениями и точными денежными единицами нужно добавить отдельно.
- Повторы временных ошибок: максимум три попытки, тайм-аут каждой — 8 секунд, нарастающая задержка со случайным разбросом. Короткий Retry-After не сокращается; при ожидании свыше двух секунд управление возвращается интерфейсу с `retryAt`, ручной повтор до этой даты блокируется.
- Ошибки доступа, договора данных и отмена автоматически не повторяются. Код ошибки преобразуется в безопасный текст; ответ сервера, секреты и stack trace в интерфейс не выводятся.
- Один и тот же запрос объединяется RTK Query. Ключ включает кабинет, период и демосценарий. Поздний ответ старого периода не подменяет новый.
- При временном сбое обновления сохраняется снимок **того же ключа** с предупреждением и датами. Ошибка доступа/контракта скрывает прежние показатели в интерфейсе. Это не полноценная система отзыва сессий: при добавлении реального входа нужно очищать все кеши кабинета и пересмотреть политику доверия.
- Поддерживается AbortSignal, включая отмену ожидания между попытками. Общий RTK-запрос не отменяется автоматически при простой отписке компонента; смена периода защищена ключами кеша. Есть тесты явной отмены и поздних ответов.
- Кеш находится в памяти текущего окна, не на диске; неиспользуемый ключ сохраняется 60 секунд. Постоянный кеш для работы без сети и межоконное объединение запросов ещё предстоят.

## Порядок подключения

1. Проверить API и схему авторизации без извлечения токенов из чужих браузерных сессий.
2. Создать явную read-only сессию клиента, хранить доступ в macOS Keychain. Не в Redux, JavaScript localStorage, исходниках или логах.
3. Согласовать агрегированный маршрут или композицию существующих read-only маршрутов. Новый серверный код готовить отдельно, не менять соседний проект без учёта его инструкций.
4. Ввести серверный адаптер и валидацию ответов; нормализовать деньги без накопления ошибок floating point. Реальные деньги сохранять как decimal-строки или минимальные денежные единицы, а не полагаться на demo numbers.
5. Реализовать срок жизни снимков, отмену запросов и защиту от позднего ответа другого кабинета. При отключении связи сохранять последний подтверждённый снимок с явным временем.
6. Сверить на одном реальном кабинете данные и суммы с SellerStatus за совпадающий период.

## Источники, которые добавляются отдельно

Возвраты продавцу — отдельный поток от возвратов покупателей на WB. Новости — официальный источник с датой и ссылкой. Статусы реальных поставок — самостоятельная интеграция. Прототип не выдаёт эти потоки за уже подключённые.

ИИ не нужен для загрузки, фильтрации, правил запаса или финансовых расчётов. Возможная будущая роль — объяснять подтверждённые показатели со ссылкой на исходные данные.
